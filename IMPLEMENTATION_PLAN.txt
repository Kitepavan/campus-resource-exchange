3. ARCHITECTURE
================================================================================

Request flow:

  Browser
    -> JSP (WEB-INF/views, JSTL/EL)
    -> Servlet (controller)
    -> Service (business rules, transactions)
    -> DAO (JDBC, PreparedStatement)
    -> MySQL

Rules:
  - JSP contains no business logic and no Java scriptlets.
  - Servlets do request parsing, validation dispatch, session checks, redirects.
  - Services enforce business rules and own database transaction boundaries.
  - DAOs contain SQL only and return domain objects; they never render HTML.
  - No Spring, Spring MVC, JPA, Hibernate, Lombok, ORM, or JS framework.

Layer responsibilities:

  model/       Domain classes, enums, interfaces.
  dao/         JDBC CRUD and queries; Connection overloads for transactions.
  service/     Auth, resources, requests, transactions, reviews, admin, backup.
  controller/  Servlets grouped by workflow.
  filter/      One SecurityFilter: session auth, role checks, CSRF.
  exception/   AppException hierarchy with user-safe messages.
  util/        Config, DB connection, BCrypt, uploads, validation, flash, CSRF.
  backup/      Serializable backup DTOs and ObjectInputFilter logic.

5. DOMAIN MODEL AND OOP MAPPING
================================================================================

Inheritance:
  User (abstract)
    - Student
    - Admin
  Resource (abstract)
    - Book
    - LabEquipment
    - StudyMaterial

  Student and Admin override abstract User behavior (dashboard route, display
  role, permission checks).
  Resource subclasses override displayDetails() with type-specific text.
  Service code operates on Resource references and calls displayDetails()
  polymorphically.

Interfaces:
  Searchable: boolean matches(String query)
    - Implemented by Resource; searches title, description, category, course.
  Sellable: BigDecimal getSalePrice()
    - Implemented by Book, LabEquipment, StudyMaterial.
  Lendable: int getLoanPeriodDays()
    - Book: 30, LabEquipment: 7, StudyMaterial: 14.
    - Used by ResourceService to validate LEND listings and show terms.

Encapsulation:
  Private fields, public getters/setters only where needed, no mutable
  collections exposed directly.

Exceptions:
  AppException (base, user-safe message)
    - ValidationException
    - NotFoundException
    - AccessDeniedException
    - ConflictException
  SQL exceptions are wrapped and logged; users never see stack traces or SQL.

Collections:
  List<T> for DAO results, request lists, transaction lists, reviews.
  Map<String,Integer> for admin dashboard statistics.
  Set<String> for allowed image extensions and allowed upload content types.
  Comparator for catalog sorting (newest first).

Enums:
  Role: STUDENT, ADMIN
  VerificationStatus: PENDING, VERIFIED, REJECTED
  ResourceType: BOOK, LAB_EQUIPMENT, STUDY_MATERIAL
  Condition: NEW, LIKE_NEW, GOOD, FAIR
  ExchangeType: SELL, LEND, DONATE
  ResourceStatus: AVAILABLE, RESERVED, LENT, UNAVAILABLE, INACTIVE
  RequestStatus: PENDING, ACCEPTED, REJECTED, CANCELLED, COMPLETED
  TransactionStatus: PENDING_HANDOVER, ACTIVE_LOAN, COMPLETED

Domain fields (common):
  User: userId, fullName, email, passwordHash, studentId, department,
        yearOfStudy, role, verificationStatus, active, createdAt, updatedAt.
  Resource: resourceId, ownerId, title, description, category, resourceType,
        condition, exchangeType, price, lendingTerms, courseCode,
        pickupLocation, imagePath, status, createdAt, updatedAt.
  ResourceRequest: requestId, resourceId, requesterId, message, status,
        createdAt, updatedAt.
  Transaction: transactionId, requestId, ownerId, requesterId, exchangeType,
        status, createdAt, completedAt, returnedAt.
  Review: reviewId, transactionId, reviewerId, rating, comment, createdAt.

  verification_status ENUM('PENDING','VERIFIED','REJECTED')

  updated_at          TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP

  resource_id     INT AUTO_INCREMENT PRIMARY KEY
  owner_id        INT NOT NULL
  title           VARCHAR(150) NOT NULL
  description     TEXT NOT NULL
  category        VARCHAR(80) NOT NULL
  resource_type   ENUM('BOOK','LAB_EQUIPMENT','STUDY_MATERIAL') NOT NULL
  condition       ENUM('NEW','LIKE_NEW','GOOD','FAIR') NOT NULL
  exchange_type   ENUM('SELL','LEND','DONATE') NOT NULL
  price           DECIMAL(10,2) NULL
  lending_terms   VARCHAR(500) NULL
  course_code     VARCHAR(20) NULL
  pickup_location VARCHAR(150) NOT NULL
  image_path      VARCHAR(255) NULL
  status          ENUM('AVAILABLE','RESERVED','LENT','UNAVAILABLE','INACTIVE')
                  NOT NULL DEFAULT 'AVAILABLE'
  created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
  updated_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
                  ON UPDATE CURRENT_TIMESTAMP
  CONSTRAINT fk_resources_owner FOREIGN KEY (owner_id)
    REFERENCES users(user_id) ON DELETE RESTRICT
  CHECK (price IS NULL OR price >= 0)
  INDEX idx_resources_search (status, exchange_type, resource_type, condition)
  INDEX idx_resources_course (course_code)
  INDEX idx_resources_owner (owner_id)
  INDEX idx_resources_price (price)

resource_requests
  request_id    INT AUTO_INCREMENT PRIMARY KEY
  resource_id   INT NOT NULL
  requester_id  INT NOT NULL
  message       VARCHAR(1000) NULL
  status        ENUM('PENDING','ACCEPTED','REJECTED','CANCELLED','COMPLETED')
                NOT NULL DEFAULT 'PENDING'
  created_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
  updated_at    TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
                ON UPDATE CURRENT_TIMESTAMP
  FOREIGN KEY (resource_id) REFERENCES resources(resource_id)
    ON DELETE RESTRICT
  FOREIGN KEY (requester_id) REFERENCES users(user_id)
    ON DELETE RESTRICT
  INDEX idx_requests_resource_status (resource_id, status)
  INDEX idx_requests_requester_status (requester_id, status)

exchange_transactions
  transaction_id INT AUTO_INCREMENT PRIMARY KEY
  request_id     INT NOT NULL UNIQUE
  owner_id       INT NOT NULL
  requester_id   INT NOT NULL
  exchange_type  ENUM('SELL','LEND','DONATE') NOT NULL
  status         ENUM('PENDING_HANDOVER','ACTIVE_LOAN','COMPLETED')
                 NOT NULL DEFAULT 'PENDING_HANDOVER'
  created_at     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
  completed_at   TIMESTAMP NULL
  returned_at    TIMESTAMP NULL
  FOREIGN KEY (request_id) REFERENCES resource_requests(request_id)
    ON DELETE RESTRICT
  FOREIGN KEY (owner_id) REFERENCES users(user_id) ON DELETE RESTRICT
  FOREIGN KEY (requester_id) REFERENCES users(user_id) ON DELETE RESTRICT
  INDEX idx_transactions_owner (owner_id, status)
  INDEX idx_transactions_requester (requester_id, status)

reviews
  review_id      INT AUTO_INCREMENT PRIMARY KEY
  transaction_id INT NOT NULL UNIQUE
  reviewer_id    INT NOT NULL
  rating         TINYINT NOT NULL
  comment        VARCHAR(1000) NULL
  created_at     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
  FOREIGN KEY (transaction_id) REFERENCES exchange_transactions(transaction_id)
    ON DELETE RESTRICT
  FOREIGN KEY (reviewer_id) REFERENCES users(user_id) ON DELETE RESTRICT
  CHECK (rating BETWEEN 1 AND 5)
  INDEX idx_reviews_reviewer (reviewer_id)

Historical safety:
  - No hard deletes of users, resources, requests, transactions, or reviews.
  - Resource removal is a status change to INACTIVE.
  - User suspension is is_active = FALSE (login blocked).
  - FK delete behavior is RESTRICT.
  - Unique keys: users.email, users.student_id, exchange_transactions.request_id,
    reviews.transaction_id.

7. STATE MACHINES AND BUSINESS RULES
================================================================================

Resource:
  AVAILABLE -> RESERVED       when a request is accepted
  RESERVED  -> LENT           when a LEND handover is confirmed
  RESERVED  -> UNAVAILABLE    when a SELL/DONATE transaction completes
  LENT      -> AVAILABLE      when a loan is returned (unless INACTIVE)
  any       -> INACTIVE       owner deactivates or admin moderates
  RESERVED/LENT listings cannot be edited or deactivated by the owner;
  an administrator may still deactivate them.

Request:
  PENDING -> ACCEPTED         owner accepts
  PENDING -> REJECTED         owner rejects
  PENDING -> CANCELLED        requester cancels
  ACCEPTED -> COMPLETED       associated transaction completes

Transaction:
  PENDING_HANDOVER -> COMPLETED       SELL/DONATE, owner or requester
  PENDING_HANDOVER -> ACTIVE_LOAN     LEND, owner
  ACTIVE_LOAN      -> COMPLETED       LEND return, owner

Acceptance rule (single database transaction):
  1. SELECT the request and its resource FOR UPDATE.
  2. Require request.status = PENDING.
  3. Require the acting user is the resource owner.
  4. Require resource.status = AVAILABLE.
  5. UPDATE resources SET status='RESERVED'
     WHERE resource_id=? AND status='AVAILABLE'; require 1 row.
  6. UPDATE resource_requests SET status='ACCEPTED'
     WHERE request_id=? AND status='PENDING'; require 1 row.
  7. INSERT exchange_transactions (request_id UNIQUE).
  8. COMMIT; roll back on any failure.
  Because the request row is locked and request_id is UNIQUE, a second
  acceptance cannot reserve the resource twice or create a second transaction.

Request creation rule (single database transaction):
  1. Lock the resource row FOR UPDATE.
  2. Require resource.status = AVAILABLE.
  3. Require requester != owner.
  4. Require requester is VERIFIED and active.
  5. Reject an existing PENDING or ACCEPTED request for the same
     requester/resource pair.
  6. INSERT the request.

Other rules:
  - Only verified, active students may create listings or submit requests.
  - Unverified students may browse and view listings.
  - A student cannot edit or delete another student's listing.
  - Only the requester may cancel a PENDING request.
  - Only the owner may accept or reject.
  - Only transaction participants may view or update a transaction.
  - Reviews only by the requester, only after COMPLETED, one per transaction.
  - Rating 1..5 enforced in the service and by a database CHECK.
  - Admins cannot use student-only listing/request operations unless the
    specification explicitly allows it; role checks are server-side.
  - Client-supplied userId, role, price, status, ownerId, and timestamps are
    never trusted.

9. SECURITY
================================================================================

Authentication:
  - BCrypt hashing (cost 12); plaintext passwords are never stored or logged.
  - Login verifies hash, rejects inactive users.
  - On success: request.changeSessionId(), then store userId, role,
    displayName, csrfToken in the session.
  - Logout invalidates the session.
  - Session timeout: 30 minutes; HttpOnly cookie; SameSite not set by Tomcat
    by default, documented.

Authorization:
  - SecurityFilter mapped to /*.
  - Public paths: /, /login, /register, /logout, /resources, /resources/view,
    /images/*, /assets/*, error pages.
  - /admin/* requires ADMIN.
  - Student workflows require STUDENT.
  - Service methods re-check ownership and role; filters are not the only gate.

CSRF:
  - SecurityFilter checks a session-bound _csrf token on POST.
  - Every form includes the token as a hidden field.
  - Multipart create/edit forms are checked inside ResourceServlet after
    parts are parsed (filter skips multipart only).

Input and output:
  - Server-side validation for every form.
  - PreparedStatement for all SQL parameters; no string concatenation.
  - JSTL c:out for user data; no raw HTML rendering.
  - Uploads: extension/content/ImageIO validation, 5 MB limit, UUID filename,
    configured directory outside the WAR.
  - ImageServlet accepts only generated filenames matching
    [a-f0-9-]+\.(jpg|jpeg|png|gif), resolves under UPLOAD_DIR, and returns 404
    for missing files.
  - Errors show safe messages; stack traces and SQL errors go to server logs.

Session and secrets:
  - DB password, upload dir, and backup dir come from environment variables.
  - No credentials in the repository or in serialized backups.
  - Backup files are server-generated names only; no user-supplied paths.

11. SERIALIZATION AND BACKUP
================================================================================

Backup directory: ~/campus-exchange/backups (override with BACKUP_DIR).

ResourceCatalogBackup implements Serializable:
  serialVersionUID
  createdAt (String)
  List<ResourceBackupItem> items

ResourceBackupItem implements Serializable:
  ownerId, title, description, category, resourceType, condition,
  exchangeType, price, lendingTerms, courseCode, pickupLocation, imagePath,
  status.

Create:
  - Admin only.
  - Read all resources through ResourceDAO.
  - Write ObjectOutputStream to catalog-YYYYMMDD-HHmmss.ser under BACKUP_DIR.
  - Never include users, password hashes, sessions, or credentials.

Restore:
  - Admin only; filename chosen from the server-side listing, never a path.
  - ObjectInputStream with an ObjectInputFilter allowlist:
      com.campus.exchange.backup.*
      com.campus.exchange.model.*
      java.util.ArrayList
      java.lang.String
      java.math.BigDecimal
      !*
  - Reject corrupt, truncated, oversized, or disallowed-class files with a
    safe error.
  - Validate every item (enums, price/exchange rules, owner exists) before
    writing anything.
  - Restore through ResourceService/ResourceDAO inside one transaction.
  - Skip items whose ownerId + title already exist; never wipe existing data.
  - Document that restore is additive/idempotent, not a replacement.

Tests:
  - Round trip create -> restore -> expected listings.
  - Invalid class / corrupted file rejected.
  - No password fields exist in the DTO.

17. RISKS AND MITIGATIONS
================================================================================

MySQL access
  - root uses auth_socket; the user must run the SQL block with sudo.
  - Mitigation: one documented command block; app user gets only
    campus_exchange.* privileges.

Maven/Tomcat absent
  - Mitigation: portable tarballs in ~/tools; no system changes, no sudo.

JDK mismatch
  - Default java is 25, javac is 21.
  - Mitigation: pin JAVA_HOME=JDK 21 for Maven and Tomcat; release 17 bytecode.

Serialization security
  - Java deserialization is dangerous with untrusted input.
  - Mitigation: admin-only, server-generated files only, ObjectInputFilter
    allowlist, size/depth limits, validation before restore, no arbitrary paths.

CSRF with multipart
  - The auth filter cannot reliably read multipart fields before the servlet.
  - Mitigation: the filter skips multipart; ResourceServlet validates _csrf
    after parts are parsed.

Database tests
  - Unit tests use Mockito, so they do not prove SQL correctness.
  - Mitigation: schema load, sample data, and the full curl smoke workflow
    against MySQL in Phase 8.

Tomcat port conflict
  - Port 8080 is currently free; if occupied, change the connector port and
    update BASE_URL.

No browser automation
  - Mitigation: curl smoke script plus a manual browser checklist for layout
    and accessibility.

18. DELIBERATE V1 LIMITATIONS
================================================================================

Excluded by the specification:
  - Online payments, real-time chat, external university verification APIs,
    real-time notifications, AI recommendations, delivery/logistics,
    microservices.

Deliberately deferred:
  - OVERDUE transaction status and reminders.
  - Transaction CANCELLED flow after acceptance.
  - "Other" resource type.
  - Email verification, password reset, email notifications.
  - Listing reactivation after deactivation (admin/owner).
  - Backup download through the browser.
  - Pagination of catalog/admin lists.
  - Image thumbnails, cropping, or multiple images.
  - Audit log and soft-delete restoration.
  - Automated browser/UI tests.
  - CSRF protection on multipart forms is enforced in the servlet, not the
    global filter.

These are documented in README rather than claimed as complete.
